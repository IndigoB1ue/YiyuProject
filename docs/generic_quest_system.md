# 通用任务系统与配置

本版采用任务 Resource、专用配置面板、顺序阶段和阶段内并行目标。正式 demo 继续使用原有“制作清洗剂”任务和剧情路线；学生委托只存在于独立验收场景，不加入正式任务目录、场景入口或剧情。

## 在编辑器中配置

在 Godot 中启用 `addons/quest_editor/plugin.cfg` 后，打开顶部“任务配置”主界面。编辑工作副本后点击保存才会写入项目，支持撤销、重做、还原和未保存提醒。

配置一条任务的顺序：

1. 新建任务，填写稳定任务 ID、名称、说明、分类和可选学生 ID。
2. 添加接取条件。所有接取条件满足后允许接取；勾选自动接取后由状态变化或场景进入触发检查。
3. 添加、命名并排序阶段。每个阶段具有稳定 ID，达成规则可选 `all` 或 `any`。
4. 给阶段添加目标，选择目标类型及其参数。常用物品、配方、任务和剧情引用通过目录选择。
5. 如有需要，配置任务完成后的动作，例如请求剧情、接取下一任务或发放物品。
6. 查看公开信息预览、执行“检查全部配置”，修复错误后保存。保存时会更新任务目录，不需要再修改运行脚本的 preload 列表。

剧情衔接有单独配置页：填写稳定剧情 ID、Dialogic 文件、正常结束信号，可选允许播放的场景与完成后返回场景。交谈剧情还应配置交谈对象 ID 和话题 ID。剧情中需要在正常结尾发送与配置相同的信号。

已有稳定 ID 用于存档，不应通过改名表示新任务。复制任务后使用新的 ID；发布后删除阶段或目标，需要明确存档迁移策略。编辑器会检查空目标、重复 ID、无效数量及引用等错误。

## 数据与职责

| 数据或服务 | 职责 |
| --- | --- |
| `QuestCatalog` | 统一登记任务和剧情资源；生产目录位于 `data/quests/catalog.tres` |
| `QuestData` | 任务元信息、接取条件、阶段、完成动作、可选学生和教学辅助 ID |
| `QuestStageData` | 阶段 ID、文案、全部／任一达成规则及目标集合 |
| `QuestObjectiveData` | 目标类型、目标参数、公开文案、历史事件与可见性策略 |
| `QuestConditionData` | 只读接取条件，如前置任务、配方、物品、剧情、事实或场景 |
| `QuestActionData` | 带稳定动作 ID 的完成动作请求 |
| `QuestManager`（QuestSystem 单例） | 条件检查、目标记录、阶段推进、追踪、动作执行记录、任务存档 |
| `QuestFlowRunner`（QuestFlow 单例） | 执行完成动作，对接 Dialogic，保存播放身份并区分完成和中断 |
| `QuestDeliveryService` | 验证指定任务和接收人，通过背包交换接口真实扣物后报告交付事实 |

任务资源只保存定义，玩家的计数、完成状态和动作收据另存；运行时不会把玩家进度写回 Resource。

## 目标类型

| kind | 主要参数 | 完成依据 |
| --- | --- | --- |
| `have_item` | `target_id`、`amount` | 当前背包中的物品数量 |
| `recipe_known` | `target_id`、配方相关引用 | 配方解锁或有效配方道具 |
| `recipe_materials` | `recipe` | 实际配方的公开必需素材同时齐备 |
| `craft_confirmed` | `recipe`、`target_id`、`amount` | 指定配方和产物的真实成功结果确认 |
| `talk` | `actor_id`、`topic_id`、可选剧情 `target_id` | 指定交谈正常完成 |
| `delivery` | `actor_id`、`items` | 指定接收人收到真实扣除的物品 |
| `story_completed` | `target_id` | 指定剧情正常完成 |
| `fact` | `target_id`、`amount` | 明确报告或记录的业务事实 |

`all` 阶段中的当前库存条件要同时满足，不能把不同时刻持有过的物品分别锁存后凑成“备齐”。整个阶段达成后才保留完成记录，后续物品消耗不使阶段倒退。

`any` 阶段记录实际达成的备选目标；未采用的目标不会被错误标为完成。玩家日志和配置预览会标明“任一目标达成”。

事件型目标默认只统计该目标激活后的事件。需要认可历史时可配置 `include_history`，由业务事实判断；不会通过库存反推曾经制作、交付或交谈。一次事件仅处理入站时已经激活的目标，不会在连续推进阶段时重新使用同一事件。

交付必须指定任务、目标和接收人。同一批物品只记入选择的交付目标；错误对象、缺少物品或恢复存档期间不会扣除物品。行为与动作执行的事务窗口内不允许保存中间状态。

交付历史还包含所属阶段，同一角色、物品或目标 ID 出现在其他任务或后续阶段中，也不会重复利用上一批交付。

任务列表只接收公开目标视图。推理配方隐藏答案不进入素材计数、编辑器玩家预览或房间目标描边。

## 剧情与完成动作

任务目标达成后记录任务完成和待执行动作，动作执行器负责实际播放剧情、接取后续任务或发放物品。动作 ID 与执行收据一起存档，已完成动作不重复执行；失败动作保留待处理状态。同轮动作按配置顺序尝试，但各效果独立，某项失败或剧情正在播放不会阻塞其他动作。需要“剧情看完以后再接下一任务”时，应配置剧情完成前置条件或目标，不能依赖动作数组顺序表达等待。

剧情配置的正常结束信号必须来自当前匹配的 Dialogic timeline 和播放实例。`timeline_ended` 包含外部中断，因此不能独自证明剧情已看完。

读档先校验各系统，再冻结监听、清理旧对话并恢复库存、进度、任务、动作、剧情记录和 Dialogic 位置。恢复期间不重新接取、发奖励或从头启动剧情。未开始或被中断的待播剧情保留，下一次允许的内容入口可重试。

## 现有 demo 的兼容

`make_cleanser`、`get_recipe`、`collect_materials`、`craft` 的稳定 ID 保留。三个阶段改为上述通用目标配置，确认产物后任务完成，再请求原有后续剧情。该剧情正常完成后，通过兼容标记继续开放原楼梯和礼堂。

旧 `GameProgress` 的教程、领取和剧情标记继续兼容；新内容不需要逐任务增加布尔变量。旧档中的“清洗剂剧情已开始／完成”可作为曾确认制作的证据；跳过教学、进入炼金界面或库存中有清洗剂，均不能据此推断制作目标完成。

界面沿用已确认规则：宿舍和地图左上半透明追踪栏，默认收起；炼金界面隐藏追踪栏，保留任务按钮与 J；打开任务列表暂停对话，并恢复原有暂停状态。跳过教学和追踪开关独立于任务目标。

## 独立学生委托验收

在 Godot 中打开 `tests/fixtures/quest_sandbox.tscn`，按 F6。

该场景使用独立的 `quest_sandbox_catalog.tres`、临时 InventorySystem、GameProgress、QuestManager 和 QuestFlowRunner。正式任务目录不包含 `sandbox_*` 任务；场景不设置为游戏入口，也没有从正式 demo 跳入的按钮。

测试步骤：接取委托 → 与测试学生完整交谈 → 同时准备两份药草和两份清水 → 向正确对象交付 → 阅读后续剧情。完成后仅在测试进度中发放一份回复药，并接取测试后续委托。

可提前收集材料、向错误对象交付、保存／恢复测试检查点。检查点写入 `user://quest_sandbox/`，不读写正式游戏的 120 个存档槽。运行该场景时隐藏正式全局窗口，避免操作到正式背包和存档入口。

自动化入口为 `tests/quest_sandbox_test.gd`。验收包含正常交谈、联合库存条件、交付隔离、阶段锁存、中途剧情恢复、一次性奖励与后续任务，并核对正式全局背包、任务和剧情记录未被改动。

## 本版边界

本版实现顺序阶段、阶段内全部／任一目标、前置条件、学生任务链和上述目标／动作。角色移动、角色日程、昼夜切换、复杂对话分支仍由对应系统负责。

任务内互斥路线、限时失败、放弃、重复刷新和节点式编辑器未纳入本版。新增目标类型应增加目标适配逻辑及配置表单；新增已支持类型的任务只需要配置数据和绑定交互入口。

## 接入新的交互入口

配置数据定义“要做什么”，角色按钮、场景交互点仍需调用对应服务。以下 ID 仅作接口示例，不会自动加入正式 demo。

```gdscript
# 角色提供一条已登记且满足前置条件的任务。
QuestSystem.accept_quest(&"student_commission")

# 交谈使用剧情配置中的对象、话题和正常结束信号。
# 开始播放不算完成；正常结束后由 QuestFlow 报告交谈和剧情完成。
var conversation := QuestFlow.start_story(&"student_briefing")

# 交付服务检查激活目标、对象、库存，然后真实扣物并记入所选目标。
var service := QuestDeliveryService.new(QuestSystem, PlayerInventory)
var result := service.deliver(&"student_commission", &"handover", &"student_a")
if not result.ok:
    print(result.error) # 正式交互可将这段错误展示在已有提示界面中。

# 其他玩法可以报告业务事实；稳定事件 ID 可避免同一行为重复计入。
QuestSystem.report_event(&"fact", {"fact_id": &"student_helped", "amount": 1}, "student_a/help_once")
```

现有炼金界面继续通过 `QuestSystem.on_result_confirmed(result)` 提交真实领取结果，包含来源、配方、物品、数量和稳定事件 ID。不要用“进入界面”或“背包出现产物”代替这一确认事件。

增加全新目标类型时，使用 `QuestManager.register_objective_handler(kind, evaluator, matcher)`。评估器接收任务上下文、任务定义、目标定义和事件计数，返回公开的 `current`、`required`、`completed`、`has_count`；可选匹配器接收事件类型、事件参数和目标定义，返回本次应计入的数量。新类型的配置参数和校验规则也需要加入编辑器。这样可以扩展玩法适配，而不用把每条具体任务写入任务运行器。
